# Shared update validation primitives

`keel/update-contract` is an opt-in, transport-neutral validation module for future common update manifests. It is not a new wire format and does not change the existing Keel value contract or either consumer's signed manifest v1.

- `update-version-range? version minimum previous`: all supplied versions must be strict SemVer; minimum and any previous version must precede version. `#f` means no previous version; build metadata does not affect precedence.
- `update-artifact-sha256? value`: exactly 64 ASCII hexadecimal characters, either case.
- `update-artifact-size? value`: exact positive integer, in bytes.
- `update-artifact-identity? value`: a four-element list of nonempty platform, architecture and installer strings, plus a nonempty component string or `#f` for absent component. Identities compare by string content, case-sensitively. Consumers own supported identity vocabularies.
- `unique-update-artifact-identities? values`: nonempty list of valid identities, without duplicates; different components distinguish otherwise identical artifacts.

These predicates do not establish authenticity, verify signatures, decode JSON, validate URLs, choose release channels, authorize rollback or install software. Rivet and Glaze retain their legacy v1 adapters. Glaze v1 currently accepts zero-byte artifacts and does not require strict version ranges; do not silently substitute these stricter predicates in an existing v1 reader. Any future common wire version needs explicit negotiation, signed fixtures and downstream acceptance before rollout.

## Normalized records

`keel/update-manifest` provides guarded `update-artifact` and `update-manifest` structs. Artifact fields are platform, architecture, URL, SHA-256, size, installer, arguments, component and signature. The last two are independently optional (`#f`); the signature is opaque nonempty text, not evidence of authenticity. Manifest fields are application ID, version, build, channel, publication timestamp, minimum version, previous version, rollback permission, rollout percentage and artifacts. Build is positive; rollout is an exact integer in 0..100. All strings are immutable snapshots and SHA-256 is normalized to lowercase. Artifact lists must be nonempty with unique component-aware identities.

URL, timestamp and channel are nonempty strings only: adapters own syntax and policy validation, signature verification and installation authorization. Construction alone never authorizes an update. The normalized model is not a serialized schema or a replacement for legacy v1 readers; consumers must preserve the original signed bytes and apply their own legacy validation before conversion. A zero-size legacy artifact cannot be converted into this stricter model without an explicit migration decision.

## Opt-in canonical binary payload

`keel/update-manifest-codec` provides `encode-update-manifest` and `decode-update-manifest`. This is a separate format from both legacy JSON feeds, not a replacement or automatic negotiation mechanism. It uses the existing canonical Keel value encoding. The root is a closed map with string keys `format`, `application_id`, `version`, `build`, `channel`, `published_at`, `minimum_version`, `previous_version`, `rollback_allowed`, `rollout`, `artifacts`. The format string is exactly `keel-update-manifest/1`. Each artifact is a closed map with string keys `platform`, `architecture`, `url`, `sha256`, `size`, `installer`, `arguments`, `component`, `signature`. Every field is required; absent optional values use Boolean false. Integers must fit signed Int64 in the serialized form, in addition to the model constraints. Arrays retain their declared order. SHA-256 text is lowercase. The underlying codec enforces its existing byte, depth and node budgets; decoding rejects trailing bytes, noncanonical maps and representations that would change on re-encoding.

These APIs never verify a signature or authorize installation. Existing JSON signed bytes must be verified through the existing consumer adapters. No consumer should publish this binary format until version negotiation, signature-domain separation and downstream acceptance are implemented.

## Opt-in signature envelope

`keel/update-signature` defines a closed canonical Keel map with string keys `format`, `algorithm`, `key_id`, `payload`, `signature`. The format is exactly `keel-update-manifest-signature/1`, algorithm exactly `ed25519`. Key IDs are 1..128 ASCII letters, digits, periods, underscores or hyphens. Payload is nonempty bytes, signature exactly 64 bytes. The existing Keel codec budgets also constrain the encoded envelope and signing input, so payloads near the total byte limit may be rejected. The signing input is the canonical Keel encoding of a four-element list: format string, algorithm string, key ID string, exact payload bytes. It is not the legacy JSON signing input and must never be used for Permit credentials. No canonicalization of the payload precedes verification.

`verify-update-signature-envelope` calls the caller's trusted verifier with key ID, signing input and signature, and decodes the payload only after an exact Boolean true result. Unknown keys, unauthorized keys, algorithm verification and trust scope must be enforced by that callback. Exceptions propagate and non-true results fail closed. Envelope construction and decoding alone confer no trust. The returned normalized manifest does not authorize installation; application identity, channel, freshness, rollback, URLs and artifact verification remain consumer responsibilities. Tests use synthetic verifier fixtures, not cryptographic proof. Independent Ed25519 signed vectors and actual downstream integration remain required before publishing this format.

The known-answer fixture in `keel-test/keel-update-signature.rkt` uses the public RFC 8032 TEST 1 seed and independent Python cryptography Ed25519 signing over independently encoded Keel bytes. The Racket regression pins the exact signing input and preserves the real signature bytes in envelope round trips. It does not itself verify Ed25519; consumers still need an actual provider-backed verification test. Never use the public fixture key in production.
